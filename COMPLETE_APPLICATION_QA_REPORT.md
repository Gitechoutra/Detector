# FraudShield – Complete Application QA Report

**Date:** 3 November 2026 · **Scope:** backend (Flask + MySQL), frontend (React + Vite), database and migrations
**Environment:** local development machine, Windows 11, MySQL 8.0, Python 3.14.6, Node 24, Chromium (Playwright 1.64)

All results below come from tests that were actually run. Anything that was not run is listed in
[§8 Not covered](#8-not-covered--remaining-work), with the reason.

**Health assessment:** the fraud logic, access control and investigation workflow were already well designed.
The serious problems were underneath them. The row locks guarding money movement did nothing under MySQL's
default isolation level, so parallel requests could spend the same balance twice or authorize one payment
several times. The migration history had been replaced locally, so the database had silently drifted from
the code. That drift caused the reported 500 on "NO, I did not initiate this transaction". Both problems
are fixed and covered by tests. On the evidence of the tests run, the application is now stable for its
intended use as a simulated bank. §8 lists what still needs doing before real-money use.

## 3. Bugs

Severity: **Critical** = money or authorization integrity · **High** = core feature broken ·
**Medium** = crash, security weakness or broken layout · **Low** = quality.

### BUG-01 · Critical · Row locks did not protect balances, OTPs, answers or detective decisions
- **Affected:** send money, YES + OTP authorization, YES/NO answer, investigation decisions.
- **Reproduce:** 6 parallel ₹5,000 payments from an account holding ₹20,000 → all 6 completed. 4 parallel
  submissions of one correct OTP → the payment was "authorized" 4 times. Parallel YES and NO → both accepted.
  6 parallel decisions on one case → all 6 succeeded.
- **Root cause:** the code locks a row (`SELECT … FOR UPDATE`) and then reads it with a plain `SELECT`. Under
  MySQL's default `REPEATABLE READ` that plain read returns the transaction's *first snapshot*, not the row it
  just locked. Every request waited correctly for the lock, then decided using stale balances and statuses.
- **Fix:** `config/config.py` sets `isolation_level='READ COMMITTED'` (the root cause). As a second layer,
  the lock helpers (`_lock_accounts`, `_lock_txn`, `_settle`, `_lock_case`) now *load* the rows with the lock
  (`with_for_update`), and a locking read is always current.
- **Retest:** `tests/test_qa_concurrency.py` – 7 / 7 pass. With only the isolation-level change the same 7 pass,
  which confirms the diagnosis.

### BUG-02 · High · Migration history replaced; database drifted from the code (the reported 500)
- **Affected:** "NO, I did not initiate this transaction" (dashboard and notifications), fresh installs, the
  whole test suite.
- **Reproduce:** answer NO → `500` with `Check constraint 'ck_account_status' is violated`. `pytest` → all 178
  tests error with `Failed to open the referenced table 'users'`.
- **Root cause:** the committed migrations `0001`–`0012` had been deleted locally and replaced by an
  autogenerated `262bfda3f01a` (the README says never to autogenerate). That file only added three tables, so
  an empty database could not be built. The dev database never received what `0009`–`0012` do – including
  the `BLOCKED` account status that NO sets on the receiver.
- **Fix:** restored `0001`–`0013` and `env.py` from git (the autogenerated file and the old folder are backed up,
  not deleted). Took a `mysqldump` backup of the dev database, re-applied `0009`–`0013` (all idempotent), and
  aligned the three autogenerated tables (missing defaults and `ck_receiver_block_status`). A schema diff
  between the dev database and one built fresh by the migrations now shows **0 differences** in columns,
  checks, indexes, foreign keys, triggers and views.
- **Retest:** full suite builds its database from the migrations and passes. Browser tests click NO on the
  dashboard and on the notifications page: `200`, payment `CANCELLED`, no money moved, receiver blocked.

### BUG-03 · Medium · Non-numeric `location_id` crashed login, registration and payments
- **Reproduce:** `POST /api/auth/login` with `"location_id": "abc"` → `500`. Same for register and send money.
- **Root cause:** `int(location_id)` on client input without validation. For unknown emails the raw value went
  straight into an `INSERT`.
- **Fix:** `parse_location_id()` in `helpers/auth.py` validates it (`422 VALIDATION_ERROR`). Failed logins with a
  junk city are still recorded. Send money now also rejects `[]`/`{}`, which were previously ignored silently.
- **Retest:** 31 parametrized cases in `test_qa_validation.py`.

### BUG-04 · Medium · Amounts with more than 28 digits crashed the payment endpoint
- **Reproduce:** send `"amount": "1e999999"` or `10**30` → `500`.
- **Root cause:** `Decimal.quantize()` raises for values beyond its precision, and the range check ran after it.
- **Fix:** `parse_amount` checks finiteness and range first, then decimal places.
- **Retest:** 20 invalid and 3 boundary amounts in `test_qa_validation.py`.

### BUG-05 · Medium · Non-text JSON values crashed six endpoints
- **Affected:** YES/NO answer, investigation decision, watchlist add, receiver details (UPI / QR / account / IFSC),
  Frauder console fields, `idempotency_key` in the body.
- **Reproduce:** `{"response": 7}` on `/api/transactions/<id>/confirmation` → `500`.
- **Root cause:** the pattern `(value or '').strip()` assumes a string. Any truthy number, boolean or list crashes.
- **Fix:** one helper, `as_text()` in `helpers/validators.py`, used at all 21 call sites. Numbers keep their digits,
  so a numeric account number still works. Anything else becomes `''` and the existing validation answers `422`.
- **Retest:** 68 cases in `test_qa_validation.py`; the API fuzzer now finds no 500 anywhere.

### BUG-06 · Medium (security) · Client IP could be spoofed with `X-Forwarded-For`
- **Impact:** the IP feeds the IP watchlist (rule R6), the auto-watchlisting of an attacker's IP after a NO, and the
  audit trail. Any client could send `X-Forwarded-For: <anything>` to slip past an IP block.
- **Fix:** `client_ip()` uses the connection address. Behind a real reverse proxy, set `TRUST_PROXY=1`. Werkzeug's
  `ProxyFix` then takes the address the proxy appended, which a client cannot forge (documented in `.env.example`).
- **Retest:** `test_a_spoofed_forwarded_for_header_is_ignored`.

### BUG-07 · Medium (security) · No limit on password guessing across accounts
- **Impact:** each account locks after 5 failures, but one address could try passwords on any number of accounts.
- **Fix:** 20 failed sign-ins from one address in 15 minutes → `429 RATE_LIMITED`. This uses the existing
  `login_attempts` table (indexed `created_at`), so there is no new dependency or migration. Frauder-console
  simulations do not count.
- **Retest:** `test_one_address_guessing_across_many_accounts_is_throttled`, `test_a_few_typos_do_not_throttle`.

### BUG-08 · Medium (UI) · Pages scrolled sideways on phones
- **Reproduce:** at 360 px the user dashboard overflowed by 43 px and Notifications by 24 px (13 px at 390 px).
- **Root cause:** `.btn { white-space: nowrap }` kept the 365 px-wide "NO, I DID NOT INITIATE THIS TRANSACTION"
  label on one line.
- **Fix:** below 560 px, buttons may wrap (`styles.css`). Short labels are unchanged. Checked visually from screenshots.
- **Retest:** `e2e/test_e2e_pages.py` at 7 viewports.

### BUG-09 · Low · Rule weights and score bands accepted `true` and `1.5`
- **Root cause:** `parse_int` used `int()`, which turns `true` into 1 and `1.5` into 1.
- **Fix:** booleans and non-whole numbers are rejected with `422`.
- **Retest:** `test_rule_weight_must_be_0_to_100`, `test_invalid_score_bands_are_refused`.

### BUG-10 · Low (performance) · One 938 KB JavaScript bundle for every visitor
- **Fix:** dashboard pages are code-split with `React.lazy`. The charts and QR libraries now load only for the role
  that uses them. Main bundle: **938 KB → 254 KB** (gzip 283 KB → 84 KB). The Vite size warning is gone.
- **Retest:** `npm run build`; all browser tests pass with the split bundle.

### Checked and found correct (not bugs)
- **R7 at exactly ₹50,000 does not fire.** By design: the structuring band is ₹45,000.00–₹49,999.99 ("just under"
  the reporting threshold).
- **R9 fires after only 2 failed logins.** Correct: the login came from a new untrusted device, which is a separate
  R9 signal. The test now checks the failed-login signal itself.
- **A restriction landing between the early check and the row locks** – `_settle` re-checks under the locks, so no
  money moves. Proven by deterministic tests.

## 9. How to run everything again

From `Detector/backend` with the virtual environment active (`.venv\Scripts\activate`, or `venv\…` on this machine):

```bash
# once
pip install -r requirements-dev.txt
python -m playwright install chromium

# API, engine, database (≈ 6½ min) – uses <db>_test, never the real database
python -m pytest -q

# one area
python -m pytest -q tests/test_qa_concurrency.py

# browser (≈ 7 min) – starts its own servers on ports 5055/3055 against <db>_e2e
python -m pytest -q e2e

# frontend build
cd ../frontend && npm run build
```

Browser failures save a screenshot, plus the backend and frontend logs, to `backend/e2e/artifacts/`.
